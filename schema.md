# Trip Log — Database foundation

Drizzle schema: `lib/db/src/schema/`. PostgreSQL is the source of truth for
foreign keys, uniqueness, checks, and generated values. All five tables from
the approved PLAN.md are implemented; no trip/stops/stays/stars API or UI exists yet.

## Columns

Required columns are NOT NULL. Optional columns are nullable.

| Table | Required columns | Optional columns |
|---|---|---|
| `users` | `id uuid PK DEFAULT gen_random_uuid()`; `clerk_user_id text UNIQUE`; `email text`; `created_at timestamptz DEFAULT now()` | — |
| `trips` | `id uuid PK DEFAULT gen_random_uuid()`; `user_id uuid FK users.id`; `title text`; `start_date date`; `end_date date`; `created_at timestamptz DEFAULT now()` | `destination_region text`; `trip_type text`; `notes text` |
| `stops` | `id uuid PK DEFAULT gen_random_uuid()`; `trip_id uuid FK trips.id`; `name text`; `latitude numeric(9,6)`; `longitude numeric(9,6)`; `sort_order integer` | `visit_date date`; `stop_type text`; `transport_from_previous text`; `notes text` |
| `stays` | `id uuid PK DEFAULT gen_random_uuid()`; `stop_id uuid UNIQUE FK stops.id`; `accommodation_type text`; `check_in date`; `check_out date` | `rating integer`; `notes text` |
| `stars` | `user_id uuid FK users.id`; `trip_id uuid FK trips.id`; `created_at timestamptz DEFAULT now()`; composite `PRIMARY KEY (user_id, trip_id)` | — |

The existing users definition is unchanged. Passwords, password hashes, session
tokens, and verification codes are never stored in these tables.

## Relationships and deletion

- User → many trips and stars.
- Trip → many ordered stops and stars.
- Stop → zero or one stay, enforced by unique `stays.stop_id`.
- Every foreign key uses `ON DELETE CASCADE`: trip deletion removes its stops,
  their stays, and its stars; stop deletion removes its stay; user deletion
  removes that user's trips and stars and their descendants.
- Deleting a stay does not delete its stop, trip, or user. Deleting a trip does
  not delete its user or unrelated trips.

Drizzle `relations` definitions expose the same graph for typed relational
queries. UUIDs are generated by PostgreSQL, not by application code.

## Constraints and indexes

- Titles and stop names must contain a non-whitespace character.
- Trip end date ≥ start date; same-day trips are valid.
- Latitude −90…90; longitude −180…180; sort order ≥ 0.
- Allowed transport values: `Driving`, `Flying`, `Other`, or NULL.
- Stay check-out > check-in; optional integer rating 1…5.
- Allowed accommodation values: `Hotel`, `Campground`, `Vacation Rental`, `Other`.
- `trip_type` and `stop_type` remain optional free text as approved.
- Owner/date index: `trips(user_id, start_date)`.
- Stop itinerary index: `stops(trip_id, sort_order)`.
- Unique stop/stay index covers stay-to-stop lookups.
- Stars' composite PK covers user/trip lookup; `stars(trip_id)` supports reverse
  lookups and cascade deletion.

Transport/accommodation labels above are the concrete text vocabulary for the
approved categories; column types remain `text`, not PostgreSQL enum types.
Stop positions deliberately are not unique, so future atomic reordering can
temporarily use matching positions. No reordering operation is implemented yet.

Calendar dates use Drizzle string mode (`YYYY-MM-DD`); timestamps use instants
with time zones. Numeric coordinates return decimal strings to preserve precision.
Model insert schemas are persistence helpers, not public request DTOs.

## Authentication and future ownership

Clerk ID, not email, is the identity key. Account synchronization obtains the
verified primary email server-side and atomically upserts by the unique Clerk ID.
The internal UUID and creation timestamp remain stable.

Relational integrity is **not authorization**. Future APIs must mount `requireUser`
and scope trips—and all descendant lookups and star operations—to the internal
`res.locals.user.id`. Foreign keys alone do not prohibit one user's ID from being
paired with another user's trip in a star row. No public mutation API exists yet;
owner-only operations and comprehensive isolation tests begin with Trip CRUD.

## Applying and testing

Development only: `pnpm --filter @workspace/db run push`.
Tests: `pnpm --filter @workspace/api-server test`.
All database-test travel records are transaction-scoped and rolled back;
authentication tests remove their own uniquely identified synthetic users.

Managed production schema changes happen through the owner's Publish flow after
review/merge. No production DDL, startup migrations, or deploy-build migration
script is included. The Feature 2 development schema has not been published.
